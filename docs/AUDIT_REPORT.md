### حكم موجز
النظام **يعمل كمنظومة تشغيل مدرسية مترابطة جزئيًا**، لكن المعمارية الحالية **هجين**: نواة طباعة حديثة + مسارات طباعة قديمة، وSQLite قوي للنواة التشغيلية + JSON/localStorage للجزر الإدارية، وحدث تكامل موجود لكن **غير شامل**. الخطوة الصحيحة ليست إعادة بناء، بل **توحيد الطبقة المطبوعة** ثم **ربط التغذية لغرفة القيادة**.

## 2. تفاصيل المراجعة حسب الطبقة

### 2.1 الطبقة الأولى — الطباعة (Print Layer)

#### ما هو جيد
- **`official-frame-core.js`**: مصدر واحد للترويسة (`doc-official-header`) والاعتماد (`doc-signoff-block`) و`page()` و`armPrintPage()`.
- **`print-templates.js`**: `PORTRAIT_OFFICIAL` + `PROGRAM_CARD` فوق النواة؛ ميتا زوجية؛ قص نصوص؛ شواهد؛ أعمدة توقيع برامج.
- **عقد A4 المعتمد (بعد الإصلاح الأخير):**
  - `@page official-core-a4 { margin: 0 }` يكسر تعارض `print.css` العام (`landscape` + `margin:16mm`).
  - إطار `position: fixed` + تدفق `body` بارتفاع 0 → صفحة واحدة في Chrome.
  - توقيعات باحتياطي `sig_teachers` / `sig_students` / `sig_manager`.
  - شاهد `object-fit: cover` بعرض المحتوى، مستثنى من سقف شعار الترويسة.
- محضر المجالس ومسار تحسين الشواهد يستخدمان النواة في مواضع محددة.

#### ما يحتاج إصلاح / اكتمال
| بند | الوضع الحالي | الأثر |
|-----|---------------|--------|
| النماذج الأربعة | `KINDS` فيه نوعان فقط | لا يوجد Landscape / Card / Table موحّد |
| مسارات قديمة | غياب، زيارة صف، سجلات، تسكين، جزء من التحسين، بطاقة الشاهد اللاصفية (`print-soft-witness`) | ترويسة/هوامش/توقيعات غير مضمونة بنفس عقد A4 |
| `@page` العام في `print.css` | ما زال `landscape` + `16mm` | أي مسار بلا `official-core-a4` يعود للدوامة |
| تكرار الترويسة | `officialIdentityHeader()` / `print-header-table` | صيانة مزدوجة ومخاطر انحراف الهوية |
| تقسيم الصفحات | بطاقة البرنامج: صفحة واحدة ✅ — المحاضر: متعددة مقصودة ✅ — مسارات قديمة: غير موحّدة | سلوك طباعة غير متوقع |
| تعليمات المستخدم | Chrome «تلقائي» بلا خلفيات يكسر المعاينة | فشل ظاهري رغم صحة CSS |

#### إجابات مباشرة على أسئلة الطبقة
| سؤال | الجواب |
|------|--------|
| هل الترويسة والتذييل ثابتان؟ | **داخل النواة: نعم.** خارجها: غالبًا ترويسة جدول قديمة وقد يختلف التذييل/الاعتماد. |
| هل المحتوى ينقسم إلى صفحات؟ | **مقصود** في المحاضر؛ **ممنوع** في بطاقة البرنامج (محلول). باقي المسارات غير مضمونة. |
| هل التوقيعات تظهر؟ | **نعم في مسار النواة** مع احتياطي الصور. في المسارات القديمة تعتمد على HTML محلي وقد تختفي. |

#### اقتراحات من مصادر متخصصة (طباعة) — دون تنفيذ
1. **الإبقاء على النواة الحالية لبطاقات الصفحة الواحدة** (fixed + named `@page`) — لا تستبدلها بـ `running()` الآن.
2. **للوثائق متعددة الصفحات** (محضر، كتيب): اعتماد **جدول `thead`/`tfoot`** أو تكرار ترويسة عبر محرك الصفحات الحالي — هذا موضع `running()`/`thead` حسب MDN/PrintCSS، لا موضع بطاقة البرنامج.
3. **توحيد المسارات**: كل زر طباعة رسمي → `PrintTemplates` أو `OfficialFrameCore.page` + `armPrintPage`.
4. **عزل `@page` العام**: جعله محايدًا (`margin:0`) أو إلزام كل وضع طباعة بصفحة مسمّاة.
5. **دليل مستخدم قصير داخل شريط المعاينة**: «هوامش: بلا — خلفيات: مفعّل».

### 2.3 الطبقة الثالثة — الواجهة (UI Layer)

#### خريطة الأبواب الرئيسية (`erp-nav.js`)
- مهام اليوم/الأسبوع/المتابعة، فترات لاصفية، غياب، دوام.
- لجان (فلاتر على `committees-home`).
- خطط: تشغيلية، كتيب، شرائح، **برامج**، تسكين، سجلات، لوحة قيادة، تنفيذ، متابعة.
- مؤشرات اعتماد / نافس / إنجاز.
- بوابات سجلات وزيارات وتحسين وشواهد لاصفية ومحاضر.

#### مكرر / ظل
| العنصر | التقييم |
|--------|---------|
| `dashboard.js` ملاحة قديمة + بوابات | ظل جزئي بجانب ERP — مرشح لتبسيط تدريجي |
| `programs` vs `program-records` vs `plan-seat` | وظائف مترابطة لكن قد تبدو مكررة للمستخدم |
| انتباه القيادة في موضعين | مقصود للعرض، لكن منطق التحديث مزدوج |
| صفحات HTML منفصلة (`registers.html`, `plans.html`, …) | إرث محتمل بجانب `dashboard.html` الواحد |

#### ناقص / يُضاف
- شاشة إعداد قواعد غرفة القيادة (CRUD للقواعد) — القواعد تُبذر برمجيًا.
- مؤشر واضح «آخر تحديث للإشارات».
- موحّد طباعة من كل اللوحات الحرجة عبر النواة.
- معالجة تناقض أسماء القيادة (موثّق في تقرير التنافر).

#### ما يُقترح حذفه لاحقًا (بعد موافقة)
- مسارات طباعة `print-header-table` بعد ترحيلها للنواة.
- أكواد يتيمة في `dashboard.js` (معرّفات HTML غائبة — انظر تقرير التنافر).
- ملفات CSS غير مربوطة (`main.css` إن ثبت عدم الربط).

#### ما يُقترح إعادة هيكلته
- فصل «كتالوج البرامج» عن «سجل التنفيذ/القياس» بوضوح تسمية في القائمة.
- جعل غرفة القيادة لوحة هبوط افتراضية للمدير بعد الدخول (اختياري).

### 2.4 الطبقة الرابعة — التكامل (Integration Layer)

#### ما يعمل
- **`dataHub.publish(source)`** → `dataChanged` مع قائمة `dependents`.
- مستمعون في: `erp-nav.js` (عدة لوحات)، `dashboard.js`, `slide-deck.js`.
- حفظ برامج يطلق `dataHub.publish("programs")`.
- شواهد بصرية تطلق `dataChanged` بمصدر `visual-evidence`.
- مجالس تطلق `source: "councils"`.
- غرفة القيادة تُحدَّث عند بعض مصادر `dataChanged` وعند زر «تحديث».

#### جزر معزولة / ضعيفة الارتباط
| الجزيرة | المشكلة |
|---------|---------|
| مسارات طباعة قديمة | لا علاقة لها بالتكامل، لكن تكسر تجربة «مصدر واحد» |
| لجان (JSON) | تحديث التشكيل لا يغذي الإشارات مباشرة |
| `task_bank` فارغ | المهام تعتمد مصادر أخرى؛ البنك غير مفعّل |
| جزء من الإعدادات/localStorage | قيادة وتفضيلات بلا مرور كامل على `dataHub` |
| مؤشرات/نافس | ارتباط جزئي بالإشارات عبر قواعد محددة فقط |
| صفحات HTML الفرعية | قد لا تشترك بنفس مستمعي `dashboard.html` |

#### هل كل الصفحات تتحدث تلقائيًا؟
**لا.** التحديث التلقائي موجود لمصادر معلنة في `dependents`، وليس لكل حفظ في النظام. غرفة القيادة **مركز منطقي للإشارات** لكنها ليست بعد **مركز تشغيل إلزامي** لكل حدث.

#### كيف نجعل غرفة القيادة مركز النظام؟ (اقتراح معماري)
1. **عقد حدث موحّد:** كل حفظ مهم → `dataHub.publish(source)` بقائمة مصادر معتمدة (`programs`, `tasks`, `visual-evidence`, `councils`, `soft-periods`, `improvement`, `indicators`, `leadership`).
2. **مستمع وحيد للقيادة:** عند أي من هذه المصادر → `refresh_signals()` (أو `/api/signals?refresh=1`) ثم إعادة رسم `#command-attention*`.
3. **إجراء الإشارة = تنقل لوحة:** الإبقاء على `action: board:…` مع ضمان أن `erp-nav` يفتح اللوحة ويعيد التحميل.
4. **لا تُنقل كل البيانات إلى الإشارات** — الإشارات تبقى طبقة «انتباه»، والمصدر يبقى في جداوله.
5. **لوحة القيادة كـ Hub UI:** ملخص أعداد (مهام متأخرة، شواهد ناقصة، برامج بلا تقدّم) + روابط عميقة — موجودة نواةً وتحتاج تغطية أشمل للمصادر.

## 3. الأولويات

### High
1. ترحيل مسارات الطباعة الحرجة (مجالس مكتمل جزئيًا، شاهد لاصفي، زيارة، سجلات، غياب) إلى `OfficialFrameCore` / `PrintTemplates` + `armPrintPage` — ويشمل إصلاح `openWitnessPrint` و`print-council` فورًا.
2. تحييد/`named page` لكل أوضاع `@page` لمنع عودة دوامة الهوامش.
3. ربط حفظ `erp-suite` (مهام/لاصفية/…) بـ `dataChanged` → تحديث إشارات غرفة القيادة تلقائيًا.
4. إصلاح اتساق شواهد اللاصفية: `soft_no_media` يجب أن يرى `visual_evidence` وليس `evidence_images` فقط.
5. مصدر طلاب واحد (نور API أو مزامنة `studentsRegistry1059` بعد الاستيراد).
6. تعبئة أو إيقاف `task_bank` بوضوح (لا تترك جدولًا ميتًا بلا تفسير).
7. توحيد أسماء القيادة المعتمدة (إغلاق بنود تقرير التنافر ذات الأثر على الوثائق).

### Medium
6. بناء النموذجين التاليين في الطباعة: **Landscape Official** ثم **Table Official** (الكتيبات/السجلات العرضية).
7. نقل محاضر المجالس من JSON إلى SQLite (أو طبقة مستودع موحّدة) مع الإبقاء على API.
8. تبسيط الملاحة: تقليل الظل بين `dashboard.js` و`erp-nav.js`.
9. واجهة إدارة قواعد الغرفة (تفعيل/تعطيل/شدة).
10. توثيق مرادفات الجداول (`staff`→`noor_staff`) في README/عقد بيانات.

### Low
11. نموذج Card للطباعة (بطاقات قصيرة).
12. سجل مهام طباعة / تصدير Word (مذكور في future_features).
13. تنظيف الملفات اليتيمة والظل CSS بعد جرد استخدام.
14. `print_jobs` أو إحصاءات استخدام اللوحات.

## 4. خريطة الطريق (الخطوة التالية المقترحة)

```
الآن (مكتمل نسبيًا)
  └─ نواة طباعة + بطاقة برنامج A4 + شواهد + إشارات أساسية

الموجة 1 — توحيد الطباعة (High)
  ├─ ترحيل: شاهد لاصفي، زيارة صف، غياب/سجلات
  ├─ إنهاء اعتماد print-header-table تدريجيًا
  └─ رسائل معاينة (هوامش بلا / خلفيات)

الموجة 2 — مركزية القيادة (High/Medium)
  ├─ عقد dataChanged شامل للمصادر الحرجة
  ├─ refresh_signals تلقائي
  └─ توضيح task_bank

الموجة 3 — اكتمال نماذج الطباعة (Medium)
  ├─ Landscape Official
  └─ Table Official (سجلات عريضة)

الموجة 4 — تنظيف وتوثيق (Medium/Low)
  ├─ أسماء قيادة موحّدة
  ├─ تقليل ظل dashboard.js
  └─ جرد حذف بموافقة صريحة
```

**الخطوة التالية الموصى بها عند العودة (قرار واحد):**  
اعتماد **الموجة 1** — ترحيل مسار طباعة واحد عالي الظهور (بطاقة الشاهد اللاصفية أو سجل الغياب) بالكامل إلى النواة، كإثبات قالب للتوحيد، قبل بناء نماذج جديدة.

## 5. الاقتراحات (حلول من مصادر متخصصة)

### طباعة (MDN / Print CSS / ممارسات المتصفحات)
| المشكلة | الحل الموصى به لهذا المشروع |
|---------|------------------------------|
| هوامش Chrome الافتراضية | `@page` مسمّى + هامش 0 + تعليم المستخدم «بلا» |
| تجاوز صفحة واحدة | عدم الاعتماد على `overflow:hidden`؛ استخدام fixed لصفحة واحدة أو تقسيم صريح لصفحات متعددة |
| ترويسة تتكرر كل صفحة | `thead`/`tfoot` أو محرك صفحات يكرر `OfficialFrameCore.header` — **ليس** لبطاقة البرنامج |
| RTL في الطباعة | `direction: rtl` على مستوى الصفحة المطبوعة (مطبّق في مسار النواة) |

### بيانات
| المشكلة | الحل |
|---------|------|
| أسماء جداول مختلفة عن التوقعات | طبقة تسمية/وثيقة؛ لا هجرة مزدوجة |
| JSON للجزر | مستودع تدريجي إلى SQLite للكيانات التي تدخل الإشارات |
| غياب FK | إضافة مفاتيح للكيانات الجديدة فقط؛ تجنب كسر البيانات الحالية |

### واجهة وتكامل
| المشكلة | الحل |
|---------|------|
| جزر معزولة | قائمة مصادر إلزامية لـ `dataHub.publish` |
| مركز القيادة | مستمع واحد + إعادة جلب إشارات + تنقل `board:` |
| تكرار شاشات | دمج بالتسمية والمسار لا بالحذف الفوري |

### ما لا يُنصح به الآن
- إعادة كتابة النظام من صفر.
- فرض `thead/tfoot` على بطاقة البرنامج (تحل مشكلة مختلفة).
- إنشاء جداول `staff`/`students` موازية لـ نور.
- تنفيذ اقتراحات `future_features` (Word، إطار زخرفي كامل) قبل توحيد الطباعة الحالية.
